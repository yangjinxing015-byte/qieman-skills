## 0. Skill Definition

本 Skill 不等同于“营销 H5 模板”。

它是原 `qieman-advisor-h5-design` / `qieman-design-h5` 的持续演进版本：保留原来对且慢业务 H5、策略、活动、投教、报告、诊断、功能介绍等场景的覆盖，但把“营销 H5”升级为更通用的“业务内容设计与页面化”能力。

**《日富一日》《锦上添花》等页面仅用于验证通用规则，不是本 Skill 的固定模板。**

它负责将一份业务内容，从原始材料转化为适合用户阅读和理解的完整业务页面：

```txt
业务内容 / 原型 / PRD / 文案 / 数据
↓
识别页面任务与内容类型
↓
锁定内容忠实度
↓
建立信息架构
↓
选择页面 Pattern
↓
选择视觉表达方式
↓
设计移动端页面
↓
按指定格式交付
```

**H5 / HTML 是输出方式，不是 Skill 的业务边界。**

### 0.1 Skill 的核心职责

本 Skill 必须解决以下问题：

1. 这是什么类型的业务内容？
2. 用户进入页面后最先需要理解什么？
3. 信息应该以什么顺序出现？
4. 哪些内容应该文字化，哪些应该数据化、图表化、流程化或视觉化？
5. 页面是否忠实于用户提供的原始内容？
6. 页面是否符合且慢的金融品牌气质？
7. 在没有素材包的环境中，页面是否仍能独立完成？
8. 输出是否能够直接用于验证、评审或继续设计开发？

### 0.2 与且慢基础 UI 的关系

本 Skill 的基础 UI 语言继承自 `qieman-ui-design`（L0），但**不要求运行时必须同时加载 L0 Skill**。

### Foundation Dependency Contract｜基础依赖约定

本 Skill 是主编排层，默认协调以下基础规范：

1. **`qieman-ui-design`**
   - 管页面基础 UI 与 Token
   - 包括：页面背景、白卡、字体、字号、字重、圆角、按钮、表单、基础涨跌色、spacing token

2. **`qieman-chart-design`**
   - 管图表与数据可视化表达
   - 包括：柱状图、折线图、饼图 / 环图、对比图、趋势图、收益 / 回撤 / 波动图、图例、坐标轴、标签、注释、高亮逻辑

3. **可选垂类 Skill**
   - 如 `qieman-insurance-design`、`qieman-vip-design` 等
   - 仅在对应业务语境下叠加，不作为本 Skill 的运行硬依赖

### Dependency Priority｜冲突时的优先级

当规范交叉时，使用以下优先级：

- **页面容器与基础组件** → 以 `qieman-ui-design` 为准
- **图表本体与数据可视化样式** → 以 `qieman-chart-design` 为准
- **垂类业务元素**（如保险人物 / icon / 插画语境） → 以对应垂类 Skill 为准
- **本 Skill** 负责最终内容结构重组、信息层级、视觉策略、版式整合与输出



为保证单 Skill 可独立运行，本文件内置一份精简的 **Qieman Foundation UI**：

- 基础品牌色与文字色 Token；
- 字体家族与可读性下限；
- 间距、圆角、边框与基础层级；
- Remix Icon 4.6.0 通用图标规则；
- 44px 最小触控高度；
- 风险披露最低 11px；
- 已经由实际 Figma 设计稿确认的 Business Content Typography Overrides。

冲突时遵循：

```txt
用户明确 Figma / 设计工具标注
> 本 Skill 已确认的 Business Content Override
> Qieman Foundation UI（L0）
> 通用默认值
```

保险设计、VIP 设计等更具体的垂类 Skill 可在此基础上继续叠加，但不得成为本 Skill 的运行硬依赖。

# 2. Locked Content｜内容锁定（最高优先级）

> **铁律：除非用户明确授权，否则不得改动输入材料中的任何描述、文案、数据。**
>
> **内容锁定，视觉重做。**

本规则优先级高于“优化表达”“提升可读性”“增强营销感”“补全文案”“使页面更完整”等一般设计目标。

当用户提供原型、需求稿、PRD、HTML、截图、表格、Cursor / 其他 AI 生成页面或任何包含业务内容的输入时，默认进入：

> **Locked Content Mode（内容锁定模式）**

## 2.1 默认锁定范围

以下内容默认全部锁定，必须按输入原样保留：

- 标题、主标题、副标题；
- 正文描述、说明文字、备注；
- 模块标题、标签、按钮文案、提示语；
- 风险提示、活动规则、产品规则、合规文案；
- 表格内容、列表内容、图表标题与图表文字；
- 所有数字、金额、百分比、日期、时间、单位；
- 指标名称、数据来源、统计口径；
- 用户提供的其他业务描述。

## 2.2 默认禁止行为

未经用户明确授权，不得：

- 改写、润色、精简、扩写、总结；
- 补充、删除、合并或替换原文；
- 修改措辞、语气、按钮文字或标题；
- 修改数字、单位、日期、比例、金额或数据口径；
- 为了排版、营销感或页面完整性自行新增业务文案；
- 因为发现错别字、歧义、重复或疑似数据问题而自动修正。

**即使只是为了让页面更顺、更短、更美观，也不得擅自修改原始内容。**

## 2.3 允许的设计处理

在不改变任何原始内容的前提下，可以：

- 通过字号、字重、颜色、留白和分组建立视觉层级；
- 通过卡片、分割、背景区块重新组织视觉表达；
- 将原有数据重新设计为更合适的图表、Diagram、时间轴、配置图或其他可视化形式；
- 将同一段原文拆成多个视觉区域展示，但不得删字、改字或新增业务文字；
- 在用户允许的情况下调整模块顺序。

> **数据内容必须继承，数据的视觉表达方式必须重新判断。**

## 2.4 发现原文疑似错误时

如果发现输入内容可能存在：

- 错别字；
- 表达不顺；
- 重复；
- 歧义；
- 数据异常；
- 与常识不一致。

默认仍按原文输出，不得自动修正、补全或统一口径。

只有用户明确要求“纠错 / 优化文案 / 调整内容 / 修正数据”等时，才允许修改。

## 2.5 内容修改的唯一触发条件

仅当用户明确表达以下意图时，才能退出 Locked Content Mode：

- “帮我优化文案”；
- “可以润色 / 改写”；
- “可以调整措辞 / 标题”；
- “帮我纠错”；
- “可以补充缺失内容”；
- “允许调整内容结构”；
- “数据口径按你整理”。

若用户未明确授权，默认保持：

> **文案、描述、数据不动；版式、视觉、图表、可视化重做。**

# 3. Page Routing｜页面路由与目标判断

## 3.1 生成前必须完成的判断

```txt
1. 页面是什么类型？
2. 页面首先要让用户“理解什么”？
3. 页面是否还承担行动 / 转化目标？
4. 用户提供的内容忠实度要求是什么？
5. 数据是否需要重点可视化？
6. 是否有原型 / 参考稿 / 视觉参考？
7. 当前环境是否有品牌素材？
8. 最终输出格式是什么？
```

## 3.2 One Page, One Primary Communication Goal

每个页面必须有一个主要沟通目标。

注意：**主要目标不等于 CTA。**

示例：

| 页面 | 主要沟通目标 |
|---|---|
| 策略介绍 | 让用户理解策略逻辑与风险收益特征 |
| 红利罗盘 | 让用户理解当前信号及其含义 |
| 月月分红 | 让用户理解现金流来源与运行方式 |
| 充值活动 | 让用户理解活动价值并完成充值 |
| 财富报告 | 让用户快速理解资产状态与关键结论 |
| 账户诊断 | 让用户理解账户问题和改善方向 |
| 功能介绍 | 让用户理解功能价值和使用方式 |

## 3.3 CTA Conditional Rule｜CTA 条件规则

CTA 不再是业务页面的必选组件。

### 应设置强 CTA

当页面目标明确包含：

- 领取
- 充值
- 开通
- 参与
- 使用
- 提交
- 预约
- 购买 / 跟投（在合规和业务允许时）

### 可设置弱 CTA

当页面主要是理解型内容，但存在自然后续动作：

- 查看详情
- 查看当前配置
- 咨询顾问
- 了解更多
- 查看报告

### 可以没有 CTA

当页面主要用于：

- 策略说明
- 投教
- 研究解释
- 数据复盘
- 机制说明
- 内部或顾问讲解材料

禁止为了满足模板完整性强行加入“立即购买”。

## 3.4 Bottom CTA Rule｜按钮与吸底操作区

### Button Locked Component｜按钮锁定（高优先级）

当用户提供的原型、参考图、Figma、HTML 或现有页面已经明确出现按钮时，**该按钮及其吸底操作区默认属于 Locked Component**。

> **原按钮存在 → 原按钮样式优先。未经明确授权，不得重做按钮。**

默认必须保留：

- 按钮文案；
- 宽度、高度；
- 圆角；
- 背景色 / 渐变 / 描边 / 阴影；
- 字号、字重、行高；
- 内边距与左右外边距；
- Icon 与文字关系（如原稿存在）；
- 吸底容器的高度、背景、分割线、留白、安全区；
- 按钮与页面底部、次级操作、提示文案之间的位置关系。

禁止：

- 因为“增强营销感”将原按钮改成渐变、发光、加大、加粗；
- 因为页面主题变化而替换按钮颜色或形态；
- 擅自把“查看策略详情”等原文案改成“立即买入 / 立即购买”等；
- 在原按钮已经明确的情况下套用本 Skill 的默认 CTA 样式。

只有用户明确提出“优化按钮 / 修改 CTA / 重做吸底操作区 / 按统一组件替换”时，才允许退出 Button Locked Mode。

### Fallback Default｜仅当输入没有明确按钮样式时

若页面确实需要 CTA，且输入材料**没有给出可继承的按钮视觉样式**，才使用以下且慢基础默认值（移动端 1×）：

- 主按钮高度：44px；
- 圆角：22px；
- 字号：**17px**；
- 字重：**Regular / 400**；
- 行高：**25px**；
- 背景：`#1B88EE`；
- 文字：`#FFFFFF`；
- 左右容器内边距：16px；
- 吸底容器背景：`#FFFFFF`；
- 顶部分割线：`1px solid #EAEFF5`；
- 安全区：适配 `env(safe-area-inset-bottom)`。

默认组件只作为**无来源样式时的兜底**，不得覆盖用户已经确认的产品组件。

# 4. Information Architecture｜信息架构原则

## 4.1 Understanding First

先设计“理解路径”，再设计页面模块。

一个高质量业务页面应回答：

```txt
这是什么？
↓
为什么与我有关？
↓
它是怎么运作的？
↓
为什么可信？
↓
风险 / 限制是什么？
↓
我是否需要做下一步？
```

不同页面可以省略或重排，但不得机械套用“营销转化漏斗”。

## 4.2 One Screen, One Key Message

移动端长页优先保证连续理解。

要求：

- 一屏尽量聚焦一个核心观点。
- 一张卡片不承担多个无关主题。
- 长段落拆成标题 + 结论 + 辅助说明。
- 能图表化的关系不要全部写成长文字。
- 同一层级信息不宜超过 3–5 个并列重点。

## 4.3 Information Density

避免两种极端：

**过稀：**
- 大面积纯背景
- Hero 很高但没有有效信息
- 单个 icon 占据一整屏

**过密：**
- 一张卡塞满 6–8 个观点
- 一屏同时出现多个图表
- 文字、数据、图标层级冲突

原则：

> **高价值信息密度，而不是高元素密度。**

## 4.4 Card Usage

卡片是信息容器，不是页面默认装饰。

规则：

- 不要求每个模块都放白卡。
- 避免卡片套卡片产生“盒子堆叠”。
- 同一内容层级尽量只使用一层实体卡片。
- 二级信息可用分割线、浅底、局部色块、标签区分。
- 长内容页面允许“无卡正文 + 局部重点卡”的组合。

# 5. Strategy Framework｜Strategy 场景分支（非全局模板）

策略介绍是本 Skill 的一级核心能力，不属于 Marketing 的子类型。

策略页首先解决：

> **这是什么策略、为什么这样做、怎么运作、表现与风险如何、是否适合我。**

## 5.1 Strategy Base Modules

策略介绍页可从以下模块中按需选择，不要求全部出现：

```txt
策略认知
策略定位
核心理念
投资逻辑
配置结构
运行机制
资产角色
历史表现
收益来源
风险 / 回撤
不同市场环境表现
信号机制
现金流机制
适合人群
参与 / 使用方式
数据口径
风险提示
```

## 5.2 S1｜理念解释型 Strategy Philosophy

适用：

- 永久投资组合
- 长期配置
- 全天候
- 中西合璧
- 多元资产策略

推荐结构：

```txt
一句话认识策略
→ 核心理念
→ 配置框架
→ 为什么这样配置
→ 各类资产分别承担什么角色
→ 不同环境下如何协同
→ 长期收益 / 风险特征
→ 适合谁
→ 风险说明
```

视觉优先级：

1. 配置结构图
2. 资产关系图
3. 角色矩阵
4. 长期趋势 / 回撤图
5. 主题插画（仅用于建立认知氛围）

避免：只用三个 KPI 卡 + 大插画解释复杂配置逻辑。

## 5.3 S2｜数据表现型 Strategy Performance

适用：

- 有较完整历史业绩的策略
- 强调风险收益特征的策略
- 策略阶段性表现说明

推荐结构：

```txt
策略定位
→ 核心结论
→ 关键指标
→ 历史走势
→ 回撤 / 波动
→ 分阶段或市场场景表现
→ 数据说明
→ 风险提示
```

视觉原则：

> **Chart > Decoration**

避免将趋势数据重新做成大量孤立 KPI 卡。

## 5.4 S3｜资产配置型 Asset Allocation

适用：

- 股债配置
- 国内外配置
- 多资产配置
- 风险预算
- 杠铃策略

推荐结构：

```txt
配置目标
→ 配置了什么
→ 比例 / 范围
→ 每类资产承担什么角色
→ 资产之间如何互补
→ 配置带来的风险收益特征
→ 动态调整方式（如有）
```

视觉优先：

- 环形 / 堆叠配置图
- 资产角色卡
- 二维矩阵
- 风险贡献 Diagram
- 组合关系图

## 5.5 S4｜信号与动态策略 Signal / Timing

适用：

- 红利投资罗盘
- 市场深度仪
- 发车信号
- 择时 / 动态投入
- 估值信号

推荐结构：

```txt
当前信号
→ 当前建议 / 当前含义
→ 指标是什么
→ 指标如何形成
→ 不同信号分别代表什么
→ 对应行动规则
→ 历史验证（如有）
→ 局限与风险
```

视觉优先：

- 状态 Hero
- 仪表 / 信号卡
- 区间标尺
- 历史信号时间轴
- 信号与市场关系图

此类页面禁止为了“策略感”强行加入无关的大型风景插画。

## 5.6 S5｜现金流型 Cash Flow

适用：

- 月月分红
- 定取
- 养老现金流
- 周期领取
- 分红型投资方案

推荐结构：

```txt
一句话理解现金流
→ 钱从哪里来
→ 如何产生 / 分配
→ 投入与预计现金流关系
→ 历史依据 / 测算口径
→ 本金或净值如何变化
→ 长期运行方式
→ 风险说明
```

视觉优先：

- 现金流 Flow
- 月度时间轴
- 投入 → 资产 → 收益来源 → 领取 Diagram
- 测算器
- 年 / 月对照

必须明确：

- 分红 / 定取不等于固定收益。
- 历史分红或测算不代表未来。

## 5.7 S6｜长期计划型 Long-term Plan

适用：

- 长期定投
- 目标投资计划
- 退休 / 教育等长期投资方案
- 分批建仓

推荐结构：

```txt
目标
→ 时间
→ 投入方式
→ 配置方法
→ 市场波动时如何处理
→ 调整 / 再平衡机制
→ 长期路径
→ 风险与不确定性
```

优先使用时间轴、阶段图、目标路径图，而非纯产品卡堆叠。

# 7. Hero System｜首屏系统

Hero 不使用单一固定模板。必须根据页面任务选择 Hero 类型。

## 7.1 H1｜Atmosphere Hero

适合：

- 理念型策略
- 品牌陪伴
- 长期配置
- 节日 / 主题活动

特点：

- 文案 + 主题视觉共同建立认知。
- 插画或场景应服务主题语义。
- 左文右图是常用构图，但不是唯一构图。
- 主视觉不可遮挡标题或核心信息。
- Hero 与下方内容自然衔接。

仅 Atmosphere Hero 需要考虑场景层次、主体、光源、前后景完整性。

## 7.2 H2｜Information Hero

适合：

- 普通策略介绍
- 产品介绍
- 功能说明
- 投教专题

优先表达：

```txt
标题
一句话定位
核心标签 / 关键结论
必要的轻量视觉
```

不需要为了“视觉完整”强行制造大型场景。

## 7.3 H3｜Data Hero

适合：

- 当前信号
- 诊断结果
- 报告结论
- 关键指标就是页面核心的内容

优先表达：

```txt
当前状态 / 关键数字
结论
解释
必要状态视觉
```

Data Hero 中数据与结论优先于插画。

## 7.4 First-screen Density

首屏应尽量让用户看到：

- 页面是什么
- 一句话核心认知
- 至少一组有效信息

允许首张内容模块适度上浮进入首屏。

禁止：

- Hero 中下部大面积无效留白
- 只显示标题和装饰，核心内容全部落在第二屏
- 为了固定 400px 高度而拉长背景

Hero 高度由内容决定，不再强制固定区间。

# 8. Visual Language｜视觉语言

## 8.1 Brand Tone

整体气质：

- 专业
- 可信
- 宁静
- 克制
- 清晰
- 有温度但不低幼

金融页面应避免强刺激、电商化、博彩感、暴富暗示。

## 8.2 Qieman Foundation UI｜基础 Token

业务内容页必须继承且慢基础 UI 语言。颜色、字号、圆角、间距和基础组件不得每页自由发挥。

### Color Tokens（继承 L0）

```css
:root {
  --brand-primary: #1B88EE;
  --brand-primary-pressed: #0F78D4;
  --brand-primary-focus: #1580E0;
  --brand-primary-faded: #F0F6FF;

  --text-primary: #333333;
  --text-secondary: #606060;
  --text-tertiary: #999999;
  --text-disabled: #CCCCCC;
  --text-inverse: #FFFFFF;

  --semantic-error: #FA440C;
  --semantic-warning: #EA9500;
  --semantic-success: #07AD8F;

  /* 金融涨跌语义：继承 qieman-ui-design */
  --finance-rise: var(--semantic-error);   /* 涨 / 正收益 = 红 */
  --finance-fall: var(--semantic-success); /* 跌 / 负收益 / 回撤 = 绿 */

  --surface-page: #F9FAFB;
  --surface-card: #FFFFFF;
  --surface-card-subtle: #F9FAFB;
  --border-default: #D8D8D8;
  --border-primary-subtle: #9CCBF8;
}
```

图表默认色板按以下顺序取用：

`#69B1F4` → `#F88D72` → `#FBCA74` → `#7DD4C4` → `#68E0F3` → `#ADAFE8` → `#3A7BB8` → `#FAB6A5` → `#EDC273` → `#9CCBF8` → `#C8CAEF` → `#6B9CCA`。

### Color Hard Rules

- 标题 / 核心正文优先 `#333333`，不要自行发明近黑蓝、深灰蓝作为基础正文色。
- 次级正文优先 `#606060`。
- 辅助信息优先 `#999999`，但风险披露不得用禁用色或更浅颜色隐藏。
- 唯一主行动色为 `#1B88EE`。
- 暖色仅用于明确的数据比较、收益 / 风险语义或活动强调，不作为第二套主 UI 色。
- 金融涨跌必须遵循且慢 UI 语义：**涨 / 正收益 = 红 `#FA440C`；跌 / 负收益 / 回撤 = 绿 `#07AD8F`**。
- 不得把负收益、回撤或下跌状态画成品牌蓝；品牌蓝用于品牌、交互、适合/正向业务状态，不替代金融涨跌色。
- 同一页面的收益、回撤、涨跌箭头、表格正负值、图表涨跌状态必须共用同一金融语义 Token。
- 除明确业务语义外，不用绿色作为营销主视觉；绿色可以且应该用于金融“跌 / 负收益 / 回撤”语义。

## 8.3 Typography｜Foundation + Business Content Override

默认基于 **375px / 1× 移动端画布**。字体层级必须同时满足且慢基础 UI 和实际业务设计稿。

### Typography Priority｜字号优先级

```txt
1. 用户提供的 Figma / Sketch / 设计工具明确 Typography 标注
2. 本 Skill 已确认的 Business Content Typography Override
3. qieman-ui-design L0 Typography Token
4. 合理移动端默认值
```

**禁止从缩小后的长图截图反推精确字号后写成硬规则。** 长图截图只用于判断视觉层级和相对关系。

### Font Family

- 中文：`PingFang SC, MiSans, system-ui, -apple-system, sans-serif`
- 金融数字：`MiSans, DIN Alternate, PingFang SC, system-ui, sans-serif`
- 字体文件不是运行硬依赖，不输出字体文件。

### 已确认 Business Content Typography Overrides

以下数值来自实际 Figma / 设计工具明确标注，优先于 L0 默认值：

| 层级 | 字号 | 字重 | 行高 | 状态 |
|---|---:|---:|---:|---|
| 策略 / 产品 KV 主标题 | **30px** | **Medium / 500** | **120%** | 已确认 |
| 一级模块标题 | **20px** | **Medium / 500** | **140%** | 已确认 |
| 吸底主按钮文字 | **17px** | **Regular / 400** | **25px** | 已确认 |

### 其余文字使用 L0 可读 Token

未获得明确 Figma 标注时，不再使用此前视觉估算的 28 / 18 / 14 等值作为“参考稿精确字号”，而使用且慢 L0 可读 Token：

| Token / 场景 | 字号 | 字重 | 行高 |
|---|---:|---:|---:|
| 主要正文 `body` | **16px** | 400 | 1.55 |
| 次级正文 `body-sm` | **15px** | 400 | 1.50 |
| 图例 / 辅助说明 `caption` | **14px** | 400 | 1.45 |
| 时间 / 数据来源 `caption-sm` | **12px** | 400 | 1.45 |
| 风险 / 法律披露 `micro-legal` | **11px** | 400 | 1.45 |
| 指标核心数字 `number-lg` | **28px** | 700 | 1.12 |
| 次级数字 `number-md` | **22px** | 600 | 1.20 |

二级 / 卡片标题在暂无明确业务标注时优先使用 L0 `title-sm`：**18px / 600 / 1.4**；信息密度较高时可使用不低于 16px 的标题，但不得为了塞内容连续缩小。

### Typography Hard Rules｜阅读体验铁律

- **长段落正文禁止低于 15px。**
- 标准正文优先 16px；卡片次级正文优先 15px。
- 风险披露、费用说明、免责声明必须 **≥ 11px**。
- 数据来源、日期、图表脚注建议 **≥ 12px**；只有坐标轴等高密度图表内部辅助刻度可以到 10–11px。
- 禁止使用 8px / 9px 作为正式页面文字。
- 禁止为了适配卡片高度、压缩页面长度或塞入更多内容而缩小字号。
- 空间不足时优先增加高度、换行、调整布局或拆分视觉层级。
- 同一卡片 / 同一信息块尽量不超过 3 个字号层级。
- 字号必须与字重、行高成组使用；不能只抄字号而随意使用 700 / 800 等过重字重。

### Dense Data Mode｜高密度数据区

Dense Data Mode 仅允许用于**表格、图表内部**，不得扩散到正文：

- 表头 / 图例：11–12px；
- 表格正文：12–14px；
- 坐标刻度：10–11px；
- 数据来源：12px 优先；空间确有限制时最低 11px；
- 核心数字：14px 以上，重要数据优先 18 / 22 / 28px Token。

### Multi-device Readability

必须保证常见移动端宽度下稳定可读：320 / 360 / 375 / 390 / 414px。

- 小屏适配不得通过降低基础字号完成；
- 小屏优先减少并排项、允许换行、增加模块高度、调整图例位置；
- 触控按钮 / 输入控件高度不得低于 44px；
- 大屏可增加留白，但不随意放大或改变文字层级。

## 8.4 Spacing｜单一来源与固定间距

页面间距必须继承 `qieman-ui-design` 的 spacing tokens，**业务页面不得在局部自由发明 margin / padding**。

```css
:root {
  --space-xxs: 4px;
  --space-xs: 8px;
  --space-sm: 12px;
  --space-md: 16px;
  --space-lg: 24px;
  --space-xl: 32px;
  --space-xxl: 48px;
  --space-section: 64px;

  --page-x: var(--space-md);       /* 页面左右安全边距 = 16px */
  --card-gap: var(--space-md);     /* 连续白卡间距 = 16px */
  --section-gap: var(--space-lg);  /* 常规模块组间距 = 24px */
  --card-pad-x: var(--space-md);   /* 卡片水平内边距 = 16px */
  --card-pad-y: var(--space-md);   /* 卡片垂直内边距 = 16px */
}
```

硬规则：

- 页面左右安全边距固定从 `--page-x` 读取，不在 Footer、图表、卡片等局部另写 4px / 10px / 18px 等随机值。
- 同层级连续白卡之间固定使用 `--card-gap`，当前默认值为 **16px**；同类卡片不得出现某处 8px、某处 12px、某处 24px 的随机节奏。
- 模块标题与对应内容、模块组与模块组之间使用固定 spacing token；只有有明确视觉目的时才升级到更大一档。
- 模块组之间固定使用 `--section-gap`，当前默认值为 **24px**；不得因为局部样式覆写而失去整页一致性。
- 卡片内边距统一从 `--card-pad-x / --card-pad-y` 读取；信息密集场景如需更紧，仅允许使用已有 token 档位。
- 图表标题与图 ≥ 12px；图与说明 ≥ 8px。
- 正文行高按 Typography Token 执行，不通过压缩行高或缩小字号塞内容。
- **禁止为了修一个模块而覆盖全局 `.card`、`.footer`、`.section-head` 的间距，导致其它已正确模块回归。**

> **间距只有一个真源：qieman-ui-design tokens。业务 Skill 只组合，不重新定义。**

### 8.4.1 White Card Spacing Lock｜白卡间距硬锁定

- 同层级连续白卡：固定 **16px**。
- 模块组之间：固定 **24px**。
- 卡片与卡片的间距必须从 `qieman-ui-design` token 读取，不得在局部 class、特殊 section、图表卡、适合/不适合卡中自行覆盖成其他数值。
- 任何局部优化后，都要回看整页白卡节奏是否仍统一。

## 8.5 Card System

常规卡片优先继承 L0：

```css
.card {
  background: #FFFFFF;
  border-radius: 12px;
  padding: 16px;
  border: none;
  box-shadow: 0 1px 6px rgba(51,51,51,.05);
}
```

默认不对每一张白色卡片统一描边。优先通过“浅灰页面底 + 白卡 + 固定间距 + 局部分割线”建立层级；如需轻微抬升，可使用克制的轻阴影（如 `0 1px 6px rgba(51,51,51,.05)` 或 L0 `card-soft`），不要自行添加厚重投影。

卡片规则：

- 一层卡片优先。
- 卡片内部二级分区优先用浅底、分割线、间距，而不是再套白卡。
- 同页圆角、阴影、边框保持一致。
- 全页面不建议出现“每张白卡都统一一圈描边”的做法；必要边线优先放在卡片内部的分割线、数据容器或局部说明盒子里。
- 不使用厚重悬浮阴影制造“营销组件感”。

## 8.6 Page Surface & Hero Transition｜页面背景与 KV 衔接

这是**通用业务页面基础表面与顶部承接规则**，不是某一个策略页模板。

- 页面基础背景：优先使用 `#F9FAFB` / `{colors.surface-page}`。
- 内容卡片：优先使用 `#FFFFFF` / `{colors.surface-card}`。
- 通过“浅灰页面底 + 白色卡片 / 白色内容区”建立层级。
- 重要结论、关键提示、方法说明可使用且慢 UI 的浅蓝、浅黄或低饱和语义底色做局部强调。
- 不使用每个模块一套大面积底色来制造层级。
- 不用厚重阴影代替间距和层级。

### 8.6.1 Transition Source of Truth｜顶部承接的唯一规则源

**Hero / KV 与正文如何衔接，由 `qieman-business-content-design` 负责。**

`qieman-marketing-visual-design` 只负责生成可兼容承接方式的 KV / Hero 视觉资产，不拥有正文容器结构的最终解释权。

`qieman-insurance-design` 等垂类 Skill 可以提供默认建议，但最终页面承接结构仍由本 Skill 执行。

### 8.6.2 Transition Mode｜承接模式

页面采用“顶部 Hero / KV + 下方正文”结构时，必须选择明确的 `transition_mode`：

```txt
auto
overlay-card
soft-gradient
flat-spacing
```

#### A. `overlay-card`｜卡片压接式承接

默认用于：
- 营销活动页
- 策略介绍页
- 产品介绍页
- 首屏需要承接核心说明卡 / 数据卡 / 亮点卡的页面

核心规则：
- Hero / KV 底部与正文之间必须存在**独立的承接区**。
- 承接区默认高度：**56–88px**。
- 默认推荐值：**64px**。
- 当 Hero 信息密度较高或首卡内容较重时，可扩展到 **80–88px**。
- 首张核心白卡必须**部分压在承接区上**，不能完全掉入正文区域。
- 首卡推荐上移：**20–28px**，默认 **24px**。
- 正文主 Surface 顶部圆角默认：**20px（1倍图）**。
- 首张核心白卡默认圆角：**16px**。
- 承接区不可只是空白，至少应由以下两种关系共同形成：
  - Hero 底部渐变 / 雾化
  - 正文 Surface 圆角
  - 首卡压接
- 视觉目标：像“内容从 Hero 中自然承接下来”，而不是 Hero 结束后重新起一张页面。

推荐结构：

```txt
Hero / KV
↓
56–88px Transition Zone
↓
首张核心卡上移 20–28px，压入 Transition Zone
↓
正文 Surface / 后续 Section
```

#### B. `soft-gradient`｜柔和渐变式承接

默认用于：
- 保险页
- 医疗 / 家庭保障页
- 服务陪伴型页面
- 强阅读型内容页

核心规则：
- Hero 底部通过浅蓝 / 浅白 / 极浅灰 / 低饱和暖白自然过渡到正文。
- 过渡区默认高度：**48–72px**。
- 正文主 Surface 可使用顶部 **20px** 圆角，但圆角不是唯一主语义。
- 首张核心卡可以轻压接，也可以紧随 Surface 顶部进入，但不得完全与 Hero 脱节。
- 不使用明显色带、重边线、脏灰过渡或突然变白。
- 保险页面优先表达“安心、专业、可信赖、连续”。

#### C. `flat-spacing`｜平接留白式承接

默认用于：
- 投教
- 报告
- 偏内容型专题
- 信息密度较高、强调阅读性的页面

核心规则：
- 不要求圆角，也不要求大面积渐变。
- 通过 Surface 切换、24px 模块节奏、轻分割或留白完成过渡。
- 可以是清晰平接，但必须有明确设计目的。
- 禁止“无设计的硬切”。

### 8.6.3 Auto Routing｜自动路由

当用户没有指定 `transition_mode` 时：

```txt
营销 / 策略 / 产品       → overlay-card
保险 / 医疗 / 家庭保障   → soft-gradient
投教 / 报告 / 内容专题   → flat-spacing
无法判断                 → overlay-card
```

注意：自动路由是默认建议，不是死模板。

### 8.6.4 Transition Priority｜冲突优先级

承接方式冲突时按以下顺序执行：

```txt
用户明确指定
>
当前任务已确认 / Locked Transition
>
垂类 Skill 默认值
>
Page Type 自动路由
```

一旦用户确认“这个衔接样式正确”，则视为 **Locked Transition**，后续局部迭代不得随机切换承接方式。

### 8.6.5 Transition Composition Guard｜承接构图强约束

无论选择哪种模式：

- 不允许 Hero 结束后直接切换正文白底，没有承接层。
- 不允许承接区过短，造成明显断层。
- 不允许承接区只是纯空白。
- 不允许首张核心卡完全落入正文区，与 Hero 视觉脱节。
- 不允许大空洞、过度负 margin、正文内容压住 Hero 高权重主体。
- 不允许多层浮卡、圆角互相穿插或“卡片套卡片”制造复杂层级。
- 不为了做承接而改变原始业务文案、数据、CTA、风险提示。
- 不为了过渡效果重构下方正文业务模块。
- Hero 底部高权重主体必须避开可被首卡覆盖的区域。
- 同层级连续白卡仍遵循 **16px**。
- 模块组仍遵循 **24px**。

> **承接层是页面结构的一部分，不是额外装饰。**


## 8.7 Semantic Layout Rules｜业务关系决定视觉结构

> **并列就并列，流程才用流程，重点才用强调色。**

- 只有存在明确顺序、阶段、进阶、时间关系时，才使用 `01 / 02 / 03`、Stepper、Timeline、进度线。
- 并列观点、并列特色、并列买入方式不得伪造成流程。
- “策略特色”等并列信息可使用有语义的彩色 Icon + 标题 + 正文独立展现，不强制编号。
- 分区标题前的独立编号（如单独一枚 `1` / `2` 小标签）不是必需项；如果会拉高 section 高度、打断节奏或制造额外留白，应直接去掉，或改成不额外占高的紧凑样式。
- “怎么买入”等若只是多个并列方案，不得使用纵向进度线；优先使用**有颜色的功能 Icon + 标题 + 描述**。
- 文案默认保持统一左对齐；无明确设计目的时不要随机改变对齐方式。
- “适合”使用品牌蓝 / 蓝色体系；“不适合”使用明确的红色 / 对比色体系，不使用灰色弱化否定语义。

### 8.7.1 Equal-Weight KPI Rule｜同层级核心数据等权

同一组并列核心指标（例如：累计收益、年化收益、最大回撤）默认视为**同层级 KPI**。

硬规则：

- 同层级 KPI 的数字字号、字重、行高、基线和视觉权重保持一致。
- 不允许为了“制造重点”把第一项做成超大数字、其余两项缩小，造成大大小小的视觉压力。
- 只有当业务明确说明某一项是“唯一主指标”时，才允许建立主次层级。
- 收益 / 正收益使用金融红 `#FA440C`；回撤 / 负收益使用金融绿 `#07AD8F`，但颜色差异不得伴随字号差异。
- KPI 卡应优先通过对齐、留白、语义色和标签区分，而不是通过夸张字号区分。
- 320 / 360 / 375 / 390 / 414px 下，优先缩短标签、合理换行或增加容器高度，不通过随机缩小某一项数字解决空间问题。

## 8.8 Layout Alignment & Text Width｜对齐与正文可读宽度

- 页面不得出现明显错位、漂移、压线、遮挡、重叠或视觉中心偏移。
- 图表柱体、柱顶数值、X 轴标签必须共享同一中心锚点。
- 多行类目名称使用固定宽度 / 固定高度标签区，不得因换行导致柱体与标签错位。
- Grid / Flex 子项需要可收缩时使用 `min-width: 0` / `minmax(0,1fr)` 等安全结构。
- **任何正文不得出现单字逐行换行、窄列竖排式换行。**
- Icon + 标题 + 正文组件中，标题与正文必须位于可伸缩的内容容器中；空间不足时优先改为上下结构、增加高度或正常换行。
- 不得通过压缩正文列宽或缩小字号解决布局问题。

## 8.9 Business Expression Layer｜克制的业务传播感

业务内容页不能退化成后台说明页或纯信息文档。Strategy / Product / Marketing 页面允许在不改文案、不改锁定组件的前提下增加**克制的业务传播感**。本层只负责页面内部的信息节奏与重点表达，**暂不负责 AI 背景图 / KV 插画生成**。

- 每页优先建立 1–3 个视觉重点，不把所有模块做成同等权重；
- 关键收益、相对优势、修复效率、持有体验等结论可通过**大数字 + 小面积强调底色 + 简洁图形关系**强化；
- 图表不能只有“标准组件感”，应与对应业务结论形成“图表 + 结论”组合；
- 允许浅蓝、浅黄、低饱和暖色做局部重点区，不通过整页换底色制造营销感；
- 可以通过层级、留白、数据对比、结论强化提升传播效率，但不得为了“更营销”修改按钮、文案、数据、业务结构或锁定组件；
- 不使用金币、暴富符号、夸张箭头、强促销贴纸等电商化视觉。

> **传播感来自信息重点和阅读节奏，而不是背景图或装饰堆叠。**

## 8.10 Stable Foundation & Regression Guard｜稳定骨架与回归保护

本规则用于解决“刷新一次、重新生成一次，已正确的地方又变错”的问题。

### 固定的是规则，不是某一张页面模板

本 Skill **不固定《日富一日》《锦上添花》或任何单一策略页长相**。固定的是：

- qieman-ui-design 的颜色、间距、字体、圆角、基础组件 Token；
- 页面背景与白卡关系；
- 按钮锁定规则；
- Footer / 风险提示基础规则；
- 金融涨跌语义；
- 对齐、正文可读宽度、移动端安全边距；
- 已经由用户明确确认的当前任务局部组件与布局。


### Source Prototype ≠ Locked Layout｜原型不自动成为锁定布局

`Locked Layout` 只在以下情况成立：

- 用户明确说“这个样式可以”；
- 用户明确说“这里是对的 / 保持这个版本”；
- 当前任务已经进入基于已确认设计稿的局部迭代；
- 用户明确要求沿用当前布局、视觉或构图。

**第一次读取需求 HTML / PM 原型 / Cursor 页面时，输入本身不得自动成为 Locked Layout。**

> 用户上传 HTML ≠ 用户认可其视觉。  
> Requirement Source 只锁定业务事实，不锁定视觉表现。

### 当前任务内的 Locked Layout / Locked Component

一旦用户明确说某部分“这个样式可以”“这里是对的”“保持这个版本”，该部分立即进入锁定状态。

后续迭代：

```txt
只改用户明确指出的问题模块
↓
其余已确认区域保持 DOM 关系、间距、颜色、图标、Footer、按钮和视觉样式不变
↓
不得为了方便重写整套 CSS 或重构页面骨架
```

禁止：

- 修改 A 时连带重写全局 `.card`，导致 B/C 卡片间距变化；
- 优化首屏时改坏 Footer；
- 修间距时替换已经确认的图标样式；
- 重新生成页面时随机改变按钮、颜色、圆角或模块关系；
- 用“整体重构”代替局部问题修复。

### Regression Gate

每一轮输出前必须对比上一版已确认状态，至少检查：

- 页面背景是否仍正确；
- 卡片颜色与间距是否仍正确；
- Hero→正文衔接是否回归；
- 金融涨跌色是否回归；
- 图标样式是否被无意替换；
- Footer / 风险提示边距是否回归；
- 按钮是否被修改；
- 已确认模块是否出现新的错位、溢出、单字竖排。

出现“优化 A 导致已确认 B 退化”，视为**版本回归失败**，必须修复后再交付。

# 9. Data Visualization｜且慢数据可视化 Foundation

本节提炼自 `qieman-chart-design`，作为本 Skill 的内置数据可视化基础层。**所有收益、回撤、比例、趋势、对比、分布等数据图表，默认遵循 `qieman-chart-design` 的图表语言；运行时不要求额外加载 chart Skill。**

业务内容中存在明确的数据关系时，应优先考虑数据可视化，并结合业务结论进行页面化设计。

## 9.1 Chart Selection by Meaning

| 数据关系 | 推荐表达 |
|---|---|
| 类别比较 / 排名 | 柱状图 / 条形图 |
| 时间趋势 / 净值走势 | 折线图 / 面积图 |
| 占比 / 部分与整体 | 环形图 / 堆叠条 |
| 相关性 / 风险收益二维关系 | 散点图 / 象限图 |
| 密度 / 矩阵 | 热力图 |
| 分布 | 箱线图 / 直方图 |
| 资产角色 / 配置逻辑 | Allocation Diagram / Matrix |
| 现金流 | Flow / Timeline |
| 过程阶段 | Timeline / Stepper（仅在真实顺序存在时） |
| 当前信号 | 状态卡 / 标尺 / Gauge |
| 前后变化 | 对比图 |

选择图表类型时以“用户要理解的关系”为第一依据，不机械继承原 HTML 已有图表。

## 9.2 Qieman Chart Palette

图表优先从且慢图表色板取色，不自由发明新系列色：

`#69B1F4` → `#F88D72` → `#FBCA74` → `#7DD4C4` → `#68E0F3` → `#ADAFE8` → `#3A7BB8` → `#FAB6A5` → `#EDC273` → `#9CCBF8` → `#C8CAEF` → `#6B9CCA`。

使用规则：

- 蓝色优先承载品牌 / 策略主体；
- 珊瑚红 / 暖色可用于对比、收益或重点系列；
- 中性基准可使用且慢 UI Neutral 色，不必强行占用彩色系列；
- 同一图表避免使用过多颜色，系列越少越好；
- 正负收益、风险状态需遵循业务语义，不能只按色板顺序机械分配。

## 9.3 Chart + Insight｜图表与营销结论组合

策略介绍页的数据表达默认不是“孤立图表”。优先采用：

```txt
图表标题 / 图例
↓
主体图形
↓
1 个核心结论 / 相对优势
↓
必要的数据来源、口径、风险说明
```

- 关键结论可使用浅蓝 / 浅黄等小面积强调底色；
- 重点数字可适度放大，但不能压过图表本身；
- 可加入极少量图形装饰增强记忆点，但不得改变数据含义；
- 图表与结论应共同回答一个问题，避免图在上面、文案在下面但互不关联。

## 9.4 Chart First, KPI Second

当用户需要理解“变化、比较、构成、关系”时：

> 优先使用图表，不要把所有数据拆成 KPI 数字卡。

KPI 更适合回答：

- 当前值是多少；
- 关键结果是多少；
- 页面最重要的 1–3 个数字是什么。

## 9.5 Mobile Chart Rules

- 默认适配 343px 左右的移动端内容区；
- 同屏不宜出现多个复杂图表；
- 图例数量尽量控制；
- 轴标签不得重叠、截断或漂移；
- 关键值可直接标注；
- 饼图类别过多时改用列表 + 条形 / 堆叠；
- 图表必须保留输入中已有的数据时间、口径、来源；
- 图表高度由标签长度和可读性决定，不得为压缩页面而强制缩短。

## 9.6 Chart Alignment Hard Rule

- 柱状图每根柱体、柱顶数值、X 轴标签必须严格居中对应；
- 多行类目标签必须预留固定高度，不允许侵入绘图区；
- 图例、绘图区、坐标轴、标签和说明需要共享统一容器边界；
- 标签过长时优先换行、增加高度、调整布局，禁止缩成 8px / 9px 或产生错位；
- 图表在 320 / 360 / 375 / 390 / 414px 下必须保持可读，不得发生水平溢出或视觉对象错配。

## 9.7 Financial Chart Integrity

禁止：

- 修改坐标轴制造夸张视觉但不提示；
- 改变原始占比比例；
- 将负收益画成正收益；
- 擅自平滑掉关键波动；
- 编造缺失数据；
- 用 3D 柱体、透视、面积夸张等方式误导比较关系。

## 9.8 Implementation Preference

单文件 HTML / Portable Mode 优先：

1. 内嵌 SVG / CSS / Canvas；
2. 环境明确支持时使用 Chart.js / D3 等；
3. 不得因为 CDN 或外部库不可用导致图表缺失。

实现方式服从最终稳定渲染，不要求为了“使用图表库”而引入不必要依赖。

# 10. Icon & Asset System｜图标与素材系统

## 10.1 Core Principle

**品牌资源包不是运行硬依赖。**

资源缺失只允许造成“视觉资产降级”，不得造成任务执行失败。

## 10.2 Asset Mode Detection

页面生成前判断：

```txt
品牌素材可访问？
├─ 是 → Brand Asset Mode
└─ 否 → Portable Mode
```

不要求用户手动声明模式。

## 10.3 Brand Asset Mode

当 `assets/`、品牌图标、人物、插画或官方素材可访问时：

1. 语义准确的官方资产优先复用。
2. 已有高质量资产不重复生成。
3. 同一页面不得混用明显不同的图标风格。
4. 资产必须服务信息表达，不因为“库里有”而强行使用。
5. 资源路径必须真实可访问。

**优先复用 ≠ 强制滥用。**

如果现有 Icon 与业务语义不匹配，应使用更准确的 Portable 方案或新增符合系统规范的资产。

## 10.4 Brand Logo Rule｜品牌标识规则

品牌 Logo / Wordmark 属于**官方品牌资产**，不属于通用 UI Icon 体系。

当页面出现明确的品牌主体或机构主体，例如：

- 盈米基金
- 且慢
- 盈米研究院
- 盈米 AI 开放平台
- 其他品牌素材包中已经存在的官方机构 / 产品标识

在品牌识别位必须优先调用素材包中的官方 Logo、Wordmark 或品牌标识素材。

### 10.4.1 必须优先使用官方 Logo 的位置

包括但不限于：

- 页面顶部品牌区
- Hero / KV 中的品牌识别位
- 机构介绍卡片
- 团队介绍主卡
- “由某机构管理 / 出品 / 提供”的品牌归属区
- 页面底部品牌归属区

正文段落、风险提示或普通说明文字中仅出现机构名称时，不要求重复展示 Logo。

### 10.4.2 禁止行为

- 禁止使用 Remix Icon 代替品牌 Logo。
- 禁止使用通用图形、字母组合或 CSS 图形冒充官方 Logo。
- 禁止让模型自由绘制、猜测或生成“类似”的盈米基金、且慢、盈米研究院等品牌 Logo。
- 禁止因为已有一个通用 Icon，就用它替代明确的品牌 / 机构标识。
- 禁止引用不存在或不可访问的 Logo 文件路径。

### 10.4.3 Logo Fallback

如果当前环境未提供品牌素材包、Logo 文件不可访问或无法稳定加载：

1. 不得阻塞页面生成；
2. 不得伪造 Logo；
3. 使用标准品牌文字作为降级方案，例如“盈米基金”“且慢”“盈米研究院”；
4. 保留合理的品牌识别位，待正式素材可用时可直接替换。

核心原则：

> **品牌 Logo 缺失时可以降级为标准文字，不可以降级为伪造 Logo。**

### 10.4.4 Logo 与 Icon 的职责边界

```txt
明确品牌 / 机构身份 → 官方 Logo / Wordmark
通用功能 / 信息 / 操作 → Remix Icon
业务专用但非品牌标识 → 官方业务资产或定制 SVG
数据关系 / 策略机制 → Chart / Diagram
```

---

## 10.5 Portable Mode｜无资源包降级模式

触发情况：

- 只上传了 `SKILL.md`
- 平台有包体大小限制
- `assets/` 未上传
- 文件路径不可访问
- 外部字体 / CDN 不可用

此时必须继续完成设计。

图标优先级：

```txt
1. inline SVG
2. 环境中可稳定使用的 Remix Icon / 通用图标库
3. CSS 几何图形 / 状态符号
4. 通过排版、数字、图表表达，不使用 icon
```

禁止：

- 因资源缺失停止生成。
- 要求用户必须重新上传资源才能继续。
- 引用不存在的本地路径。
- 输出破图或空白 icon。
- 使用 emoji 替代正式业务 icon。

## 10.6 Remix Icon Usage

通用 UI / 功能 / 信息图标默认使用 Remix Icon v4.6.0；品牌 Logo 不属于通用图标。

**图标稳定性规则：**

- 同一页面不混用 Emoji、Remix、Material、不同风格 SVG 等多套图标语言。
- 一旦用户确认某组图标样式正确，当前任务后续迭代必须保留，不得因重新生成随机替换。
- 修间距、Footer、图表或文案布局时，不得顺带重绘已确认图标。
- 只有用户明确要求“重做图标 / 更换图标风格”时，才进入 Icon Redesign。

且慢通用 UI Icon 默认以 **Remix Icon v4.6.0** 为基础视觉体系。

- 官方参考：`https://remixicon.com/`
- Webfont CDN：`https://cdn.jsdelivr.net/npm/remixicon@4.6.0/fonts/remixicon.css`
- 默认使用 `-line` 线性风格；仅选中 / 成功 / 强调状态可少量使用 `-fill`。
- 默认图标尺寸 20px；常用 16 / 20 / 24 / 32px；图标按钮热区 40–44px。
- 同页禁止混用 Font Awesome / Material / Lucide / Emoji 作为正式通用 UI 图标。

Remix Icon 可作为 Portable Mode 的常规 UI icon 体系。

适合：

- 功能入口
- 步骤
- 列表
- 风险提示
- 标签
- FAQ
- CTA 辅助

不应单独承担：

- 大型 Hero 主视觉
- 高价值主题插画
- 复杂业务 Diagram

## 10.7 Illustration Usage

插画应回答一个明确问题：

> “这个画面帮助用户理解了什么？”

若回答不出来，应取消或弱化插画。

策略页尤其遵循：

- 有复杂数据 → 数据优先
- 有机制关系 → Diagram 优先
- 有抽象理念 → 插画可以辅助
- 有当前状态 → 状态视觉优先

# 13. Copy & Compliance｜文案与金融可信

## 13.1 Tone

页面表达应：

- 专业但不生硬
- 清楚而不炫技
- 安抚但不制造虚假安全感
- 有解释感
- 有陪伴感
- 不制造焦虑

## 13.2 Prohibited Expressions

避免：

- 稳赚
- 保本（除非合法产品事实且原文明确）
- 闭眼买
- 错过血亏
- 必涨
- 一定赚钱
- 抄底神器
- 躺赢
- 无脑跟投
- 最强策略
- 稳赚不赔

## 13.2.1 Sticky CTA Strong Contract｜吸底 CTA 强约定

移动端业务内容页的固定吸底 CTA 属于**全局强锁定组件**，其优先级高于输入原型中的按钮样式。

### 默认唯一形态

- 吸底区域只保留 **1 个整行大按钮**。
- 按钮横向占满页面安全区，左右安全边距默认 `16px`。
- 按钮高度固定为 `50px`。
- 按钮必须使用**胶囊全圆角**：`border-radius: 999px`。
- 按钮文字：**17px / 25px line-height / Regular / 400**。
- 主按钮：`#1B88EE`。
- 按压态：`#0F78D4`。
- 吸底容器考虑 `safe-area-inset-bottom`，使用白色 / 半透明白色底，不制造复杂浮层。

推荐 CSS：

```css
.sticky-cta {
  width: 100%;
  height: 50px;
  border: 0;
  border-radius: 999px;
  background: #1B88EE;
  color: #FFFFFF;
  font-size: 17px;
  line-height: 25px;
  font-weight: 400;
}
.sticky-cta:active {
  background: #0F78D4;
}
```

### Radius Lock｜圆角锁定

固定吸底 CTA 的圆角属于**系统组件强约束**，不得继承页面通用 Radius Token。

禁止：
- `8px / 12px / 16px / 20px` 等普通卡片圆角；
- 普通圆角矩形；
- 半宽按钮；
- 双按钮；
- 左侧产品信息 + 右侧 CTA；
- 小尺寸胶囊按钮；
- 输入原型中的旧按钮样式。

只有用户明确说“本页不要吸底按钮”或“修改全局吸底规范”时，才允许例外。

> **吸底 CTA 是系统级强约定，不属于 Requirement Source 的可继承视觉。**


## 13.3 Risk Disclosure｜风险提示与 Footer 锁定

涉及投资、策略、测算、收益、历史表现时：

- 用户提供的风险提示、数据口径、来源、日期等内容必须原样保留，属于 Locked Content。
- 已经存在且被用户确认正确的 Footer / 风险提示结构，属于 Locked Foundation Component，后续局部优化不得改写。
- Footer 左右边距必须继承 `--page-x`，不得出现 4px 等脱离页面安全边距的局部值。
- Footer 与上一模块的距离使用 spacing token，不因其它模块 CSS 覆盖而改变。
- 风险提示字体不得低于 11px，且不得通过过浅颜色、折叠或隐藏降低可读性。
- 历史表现不得暗示未来必然结果。
- 测算应保留原始假设和来源。
- 若输入没有提供法务 / 风险文案，不得为了“页面完整”自行编造正式合规条款；需要时提示用户补充。

活动页如原始需求包含以下信息，必须保留：

- 活动时间
- 参与条件
- 发放规则
- 限制条件
- 其他必要规则

# 14. Source Interpretation｜输入材料身份与视觉隔离

用户提供 PRD、需求 HTML、低保真原型、业务方页面、Cursor / 其他 AI 生成页面、截图或现有页面时，必须先判断其身份。

## 14.0 Source Mode｜输入模式

默认支持两种模式：

```txt
requirement-only
visual-continuation
```

### A. `requirement-only`｜默认

除非用户明确要求保留视觉，否则：

> **输入文件默认只是 Requirement Source，不是 Visual Reference。**

只继承：

- 原始文案；
- 数据、金额、百分比、日期、单位；
- 业务规则；
- 风险提示与合规文案；
- 模块所表达的业务主题；
- 真实的业务关系；
- 必要交互与状态；
- 必须保持的业务顺序。

默认**不继承**：

- Hero 高度与构图；
- Hero → 正文承接方式；
- 原卡片数量；
- 原卡片嵌套关系；
- 原 DOM / Grid / Flex 结构；
- 原背景分区；
- 原圆角、阴影、边框；
- 原字号层级；
- 原 spacing；
- 原 Icon / Illustration 位置与形式；
- 原数据图表类型；
- 原信息可视化方式；
- 原 CSS class 与视觉代码。

核心原则：

> **继承需求关系，不继承视觉关系。**

### B. `visual-continuation`｜明确触发

仅当用户明确表达：

- “沿用当前样式”
- “保持这个布局”
- “基于现有设计优化”
- “参考这个视觉继续做”
- “不要改结构 / 构图”

才允许把输入升级为 Visual Reference，并继承用户明确要求保留的视觉关系。

---

## 14.1 Requirement Source Isolation｜原型视觉隔离

在 `requirement-only` 模式下，不允许：

```txt
输入 HTML
→ 直接改 CSS
→ 输出新 HTML
```

必须经过中间隔离层：

```txt
输入 HTML / 原型
↓
Requirement Model
↓
Semantic Reconstruction
↓
Visual Recomposition
↓
新页面
↓
再回到 Source 做内容完整性核对
```

### Requirement Model｜无样式需求模型

先从输入材料抽取：

```txt
Page Goal
Module Topics
Locked Copy
Locked Data
Business Relations
Required Order
Interaction / State
Risk / Compliance
```

此阶段**不携带原 CSS、原卡片形式、原 Hero 构图、原图表形式**。

### Semantic Reconstruction｜语义重建

根据业务语义重新判断：

- 哪些内容是并列；
- 哪些是流程；
- 哪些是因果；
- 哪些是“问题 → 原因 → 解法”；
- 哪些是核心结论；
- 哪些数据适合趋势 / 比较 / 构成 / 时间 / 配置 / 现金流表达；
- 哪些模块应合并为一个更完整的视觉主题；
- 哪些原型卡片只是排版容器，不代表真实业务层级。

**业务关系必须保留，视觉容器关系可以重建。**

例如输入原型为：

```txt
Hero
↓
3 个纵向白卡
↓
数字卡
↓
2 个对比卡
```

抽取后可能只是：

```txt
主题
3 个平行卖点
一组趋势数据
两组业务差异
```

最终可重新设计为：

```txt
Hero + 核心结论
↓
平行卖点信息区
↓
趋势图
↓
对比矩阵
```

只要业务事实与业务关系没有改变，就属于正确重设计。

---

## 14.2 Visual Recomposition｜视觉重组

在默认重设计任务中，应主动重新判断：

- Hero / KV 构图；
- Hero → 正文 `transition_mode`；
- Section 分组；
- 卡片架构；
- 数据可视化；
- Icon / Illustration；
- 信息强调方式；
- 阅读节奏。

不得为了“忠实原型”机械保留原始视觉骨架。

但是：

> **视觉重组不能改写业务逻辑。**

若原内容存在明确因果、时间顺序、流程顺序，则必须保留其真实关系；并列内容则可以自由选择更合适的视觉组合。

---

## 14.3 Data Visualization Re-evaluation Gate｜数据可视化重判

如果 Requirement Source 已包含图表、数字卡、进度条、饼图或其他数据表达，不得默认沿用原形式。

必须重新判断：

1. 数据关系：趋势 / 比较 / 构成 / 流程 / 阶段 / 现金流 / 配置 / 风险收益 / 信号；
2. 原表达是否是移动端最清晰的表达；
3. 是否应切换为折线、柱状、堆叠、环形、时间轴、配置图、矩阵、现金流图、Diagram 等；
4. 是否存在“能图形化但仍只堆 KPI / 文本卡”的问题。

图表内容遵循 Locked Content，图表表现遵循 `qieman-chart-design`。

---

## 14.4 Visual Divergence Gate｜视觉差异门

当 `source_mode = requirement-only` 时，最终输出必须证明自己是真正的视觉重设计。

以下维度中，**至少 4 项**应相较 Requirement Source 发生明显重新设计：

- Hero / KV 构图；
- Hero → 正文承接方式；
- Section 分组方式；
- 卡片架构；
- 数据可视化形式；
- Icon / Illustration 表达；
- 信息强调方式；
- 页面阅读节奏。

以下变化**不计入**有效视觉差异：

- 只换品牌色；
- 只改圆角；
- 只改 shadow；
- 只调字号；
- 只调 margin / padding；
- 原 DOM / 卡片结构基本不变，只做 CSS 美化。

如果 Source 与 Output 在核心视觉骨架上仍高度相似：

> **Visual Redesign Failed → 必须重新进行 Semantic Reconstruction / Visual Recomposition。**

### 例外

若用户明确要求：
- 保留结构；
- 保持构图；
- 只做局部美化；
- visual-continuation；

则不执行“至少 4 项差异”的硬要求，只执行用户指定范围。

---

## 14.5 Production Rule｜快速生产规则

本 Skill 是生产 Skill，不承担完整 Audit，但必须保证：

- Locked Content 不被改动；
- Requirement Source 与视觉参考身份不混淆；
- 默认先抽取需求模型，再做视觉重组；
- 不把输入 HTML 当作可直接美化的页面底稿；
- 图表重新判断；
- Page Type / transition_mode 重新判断；
- 输出前通过 Visual Divergence Gate；
- 已经被用户确认的当前版本继续执行 Regression Gate。

> **第一次根据需求 HTML 生成 = 重设计。**  
> **用户确认后的下一轮 = 稳定迭代。**


# 15. Generation Workflow｜标准生产工作流

本 Skill 沿用用户确认的标准工作流：

```txt
原型 / PRD / HTML / 文案 / 数据
        ↓
qieman-business-content-design
        ↓
初版页面 HTML
        ↓
需要更强数据表达？ → 按需叠加 qieman-chart-design
需要 KV / 插画专项？ → 按需叠加独立视觉增强 Skill
        ↓
最终版 HTML
        ↓
qieman-design-content-audit
        ↓
问题清单 / 验收
```

`qieman-business-content-design` 是主生产入口；其它 Skill 是按需增强，不应让业务方每次手动组合全部能力。

页面内部执行顺序：

```txt
STEP 0 读取当前任务是否已有用户确认的 Locked Layout / Locked Component
       - 第一次读取需求原型时，不自动建立 Locked Layout
↓
STEP 1 读取输入材料
↓
STEP 2 判断 source_mode
       - 默认 requirement-only
       - 用户明确要求沿用视觉时才 visual-continuation
↓
STEP 3 锁定 Locked Content
↓
STEP 4 建立无样式 Requirement Model
       - Page Goal / Module Topics / Copy / Data / Business Relations / Order / Risk
↓
STEP 5 执行 Semantic Reconstruction
       - 只保留真实业务关系，不保留原视觉容器关系
↓
STEP 6 判断 Page Type 与 Primary Communication Goal
↓
STEP 7 重新选择 Hero / KV → 正文 transition_mode
       - auto / rounded-surface / soft-gradient / flat-spacing
↓
STEP 8 选择合适 Pattern，但不把原型 Pattern 当模板
↓
STEP 9 调用 qieman-ui-design Foundation Tokens
↓
STEP 10 重新建立视觉信息架构与模块内部表达
↓
STEP 11 判断文字 / 图表 / Diagram / Icon / Illustration 的最佳表达
        - 数据可视化遵循 qieman-chart-design
↓
STEP 12 检测 Assets：Brand Mode / Portable Mode
↓
STEP 13 生成页面
        - 首次重设计：允许视觉重组
        - 已确认版本迭代：只修改用户明确指出区域
↓
STEP 14 Visual Divergence Gate
        - requirement-only 模式至少 4 个视觉维度明显重设计
↓
STEP 15 Data Visualization Gate
↓
STEP 16 Regression Gate
        - 仅针对用户已经确认 / 锁定的区域
↓
STEP 17 内容、数据、风险、视觉、移动端验收
↓
STEP 18 按用户要求输出 HTML / H5 / 视觉方案
```

# 16. Generation Checklist｜生成验收

## 16.1 Content

- [ ] 是否识别内容忠实度模式？
- [ ] 是否没有擅自改动关键文案？
- [ ] 数据、比例、日期、金额是否与输入一致？
- [ ] 是否没有虚构卖点或金融数据？

## 16.2 Page Type & IA

- [ ] 是否明确页面类型？
- [ ] 是否有一个主要沟通目标？
- [ ] 是否选择合适 Pattern，而非默认营销漏斗？
- [ ] 用户理解路径是否自然？
- [ ] 每个模块是否只承担清晰的信息任务？

## 16.3 Strategy Page

如为策略页：

- [ ] 是否讲清“是什么 / 为什么 / 怎么做”？
- [ ] 是否体现策略真正的机制，而非只堆收益数字？
- [ ] 有数据关系时是否优先使用图表？
- [ ] 有配置关系时是否使用 Diagram / 配置图？
- [ ] 信号型策略是否优先展示当前状态？
- [ ] 现金流型策略是否解释现金流来源？
- [ ] CTA 是否确有必要？

## 16.4 Hero

- [ ] Hero 是否匹配 Atmosphere / Information / Data 类型？
- [ ] 是否避免无效留白？

调用 qieman-business-content-design，

# 19. Invocation Interpretation｜调用语义

只要用户出现以下表达：

- “重新设计”
- “不要照搬原型”
- “内容不变，视觉重做”
- “根据附件重新生成”

默认：

```txt
source_mode = requirement-only
```

只要用户明确出现：

- “沿用当前样式”
- “保持这个布局”
- “参考现在这版继续”
- “不要改结构”
- “只优化这里”

才切换为：

```txt
source_mode = visual-continuation
```

**不要要求业务方每次重新填写完整设计规范。Skill 自己负责执行规范。**

# 20. Design Decision Priority｜冲突时的优先级

当规则之间发生冲突时，按以下顺序判断：

```txt
1. 用户明确指令
2. 原始业务事实 / 数据 / 合规要求
3. Locked Content / 已确认 Locked Component
4. 用户已确认的 Locked Layout / Locked Transition / Regression Guard
5. source_mode 与 Requirement Source Isolation
6. Content Fidelity
7. 信息理解与业务关系
8. Page Type / Pattern / transition_mode
9. qieman-ui-design / qieman-chart-design
10. Visual Divergence Gate
11. 视觉完整度
12. 素材复用
13. 装饰效果
```

其中：

> **素材复用永远不能高于语义准确性与页面理解。**

> **视觉氛围永远不能高于金融事实与数据完整性。**

> **模板完整性永远不能高于真实业务需求。**
